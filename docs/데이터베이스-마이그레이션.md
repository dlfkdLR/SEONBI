# 데이터베이스 스키마와 Flyway 마이그레이션

선비의 DB 구조는 **SQL 마이그레이션 파일(Flyway)** 로만 바꾼다. Hibernate는 시작할 때 Entity와 실제 테이블이 맞는지 **검증만** 한다(`ddl-auto: validate`). 운영 DB는 이 문서의 절차 없이 직접 건드리지 않는다.

## 1. 왜 바꿨나 (기존 방식의 문제)

- `ddl-auto=update`는 운영 DB의 스키마를 앱이 시작할 때 **조용히** 바꾼다. 배포 한 번이 DB 변경이 되고, 무엇이 언제 바뀌었는지 기록이 없다.
- 컬럼 삭제·이름 변경·타입/제약 변경은 반영하지 못해 코드와 DB가 어긋난 채로 떠 있을 수 있다.
- 새 DB, 개발자 DB, 운영 DB가 같은 구조라는 보장이 없다(개발 DB는 `down -v`로 초기화해 맞췄다).
- 제약 이름이 Entity에서 자동으로 붙는 해시 이름이라 사람이 추적하기 어렵다.

## 2. 파일 구조

```
backend/src/main/resources/db/migration/
  V1__initial_schema.sql        초기 스키마 13개 테이블 (Hibernate가 만들던 구조를 그대로 옮김)
  V2__decisions_setup_key.sql   decisions.setup_key + UNIQUE(client_id, setup_key) (초기 설정 한 번에 저장의 멱등 키)
scripts/
  schema-fingerprint.sql        컬럼·제약·인덱스 지문을 뽑는 읽기 전용 SELECT (비교용)
  db-schema-check.sh            기존 DB가 V1/V1+V2와 같은지 비교 (읽기 전용)
  db-baseline.sh                기존 DB에 baseline(버전 1)을 기록 (확인 변수 필요)
  backup-db.sh / restore-db.sh  백업·복원
backend/src/test/java/com/seonbi/FlywayMigrationTest.java   마이그레이션 검증 테스트
```

- 제약·인덱스 **이름은 Hibernate가 붙이던 이름 그대로** 둔다(`fk…`, `idx…`, `*_check`, `*_key`). 이미 `update`로 만들어진 운영 DB와 이름까지 같아야 baseline이 가능하기 때문이다.
- NULL 허용 여부와 길이도 Entity와 같다. 지금은 Entity가 허용하는 값을 DB가 막지 않게 하려고 **조이지 않았다**(예: `options.name`은 NULL 허용). 조이려면 데이터를 확인한 뒤 새 마이그레이션으로 한다.

## 3. 테이블과 관계

`decisions`(결정)가 최상위이고 나머지는 모두 `decisions.id`를 따라간다. 사용자 테이블은 없고 `decisions.client_id`(브라우저 UUID)로만 구분한다.

| 테이블 | 키 | 부모(FK, 모두 `ON DELETE CASCADE`) | 주요 제약 |
|---|---|---|---|
| decisions | PK id | — | CHECK(category, status, description ≤ 1000), UNIQUE(client_id, setup_key), 인덱스 (client_id, updated_at DESC)·(updated_at DESC, id DESC) |
| options | PK id | decisions | UNIQUE(decision_id, name) |
| criteria | PK id | decisions | UNIQUE(decision_id, name), CHECK(type, direction, input_mode, source) |
| option_values | PK (criterion_id, option_id) | options, criteria | — |
| conditions | PK id | decisions, criteria(선택) | CHECK(kind, source), 인덱스 decision_id |
| condition_satisfactions | PK (condition_id, option_id) | conditions, options | — |
| questions | PK id | decisions | UNIQUE(decision_id, seq), CHECK(type, phrasing_source, origin) |
| answers | PK id | questions, decisions | UNIQUE(question_id), CHECK(preference_kind), 인덱스 decision_id |
| estimate_snapshots | PK id | decisions | — |
| analysis_results | PK decision_id | decisions (1:1) | — |
| final_choices | PK decision_id | decisions (1:1), options | — |
| free_text_inputs | PK id | decisions, questions(선택) | CHECK(status) |
| ai_usage_logs | PK id | decisions(선택) | 인덱스 (client_id, created_at) |

- **삭제 정책**: 모든 FK는 `ON DELETE CASCADE`로 Entity의 `@OnDelete(CASCADE)`와 같다. 결정 삭제 API는 `deleted_at`만 채우는 소프트 삭제라서 평소에는 연쇄 삭제가 일어나지 않고, 정리 작업으로 행을 실제로 지울 때만 하위 데이터가 함께 지워진다. 수정(UPDATE) 정책은 PK를 바꾸지 않으므로 기본값(NO ACTION)을 그대로 쓴다.
- **생성 순서**: V1은 부모 → 자식 순서(decisions → options → criteria → option_values → conditions → condition_satisfactions → questions → answers → …)로 만들어 FK가 항상 존재하는 테이블을 가리킨다.
- `flyway_schema_history`는 Flyway가 만드는 이력 테이블(앱 테이블이 아님)이다.

## 4. 실행 방식

- 앱이 시작할 때 Flyway가 `db/migration`의 아직 적용하지 않은 파일을 **버전 순서대로** 적용하고, 그 뒤 Hibernate가 `validate`로 Entity와 테이블이 맞는지 본다. 하나라도 실패하면 **앱이 시작하지 않는다**(무시하지 않음).
- PostgreSQL의 DDL은 트랜잭션이라 마이그레이션 한 파일이 중간에 실패하면 그 파일의 변경은 모두 되돌려진다.
- 설정(`application.yml`): `baseline-on-migrate: false`(기본 거부), `validate-on-migrate: true`(적용한 파일이 바뀌면 거부), `out-of-order: false`, `clean-disabled: true`(`flyway clean` 금지).
- **새(빈) DB**: 아무것도 할 필요 없다. 앱을 띄우면 V1, V2가 적용된다. (개발용 `docker compose up`도 같다.)
- 버전: Spring Boot 3.5.16이 관리하는 Flyway 11.7.2 + `flyway-database-postgresql`, PostgreSQL 16.4에서 검증했다.

## 5. 새 테이블·컬럼을 추가하는 방법

1. Entity를 바꾼다(`domain/…`).
2. **새 파일**을 만든다. 번호는 가장 큰 번호 + 1: `V3__설명.sql` (`V` + 번호 + `__` + 영문 설명). 예: `ALTER TABLE decisions ADD COLUMN memo text;`
3. 이미 적용된 파일(V1, V2 …)은 **절대 고치지 않는다**. 체크섬이 달라져 앱이 시작하지 않는다.
4. 가능하면 되돌릴 수 있고 데이터를 지우지 않는 변경으로 쓴다. 컬럼을 NOT NULL로 조일 때는 먼저 값을 채우는 문장을 같은 파일에 둔다. `DROP`·`TRUNCATE`·`CASCADE`가 필요하면 PR에서 따로 승인받는다.
5. `./gradlew test`를 돌린다. `FlywayMigrationTest`가 빈 DB 적용·재실행·Hibernate 스키마와의 일치를 보고, 모든 `@SpringBootTest`가 `validate`로 부팅한다.
6. PR 설명에 "DB 마이그레이션 포함"과 운영 적용 전 백업이 필요함을 적는다.

## 6. 이미 운영 중인 DB에 처음 적용하는 절차

운영 DB에는 테이블과 데이터가 이미 있고 `flyway_schema_history`는 없다. 이 상태로 새 앱을 띄우면 Flyway가 `Found non-empty schema(s) … without schema history table! Use baseline()` 오류로 **시작을 거부**한다(데이터는 그대로). 아래 순서대로 한다. **배포 담당이 운영자 승인을 받은 뒤 직접 실행**하며, 자동화나 이 저장소의 CI에 넣지 않는다.

1. **백업**: `sh scripts/backup-db.sh /안전한/경로` 를 실행하고 파일이 외부(다른 서버·클라우드)에도 있는지 확인한다. 복원 연습은 임시 DB에서 먼저 해 본다(7절).
2. **스키마 비교**(읽기 전용): `TARGET_DATABASE_URL='postgresql://…/seonbi' sh scripts/db-schema-check.sh`
   - `일치: … = V1` 또는 `… = V1+V2` → 3으로 진행.
   - `불일치` → **baseline 하지 않는다.** 출력된 차이(예: 운영에만 있는 옛 컬럼, 길이·제약 차이)를 확인한다. 데이터가 있는 DB를 고치려면 별도 마이그레이션(V3…)이나 수동 SQL을 먼저 설계하고 백업 후 승인받아 적용한 뒤 다시 비교한다.
3. **baseline**: 비교가 일치한 뒤에만 `CONFIRM_BASELINE=yes … sh scripts/db-baseline.sh`(환경변수는 스크립트 머리말 참조). 이 스크립트는 한 번 더 비교를 하고, `flyway_schema_history` 테이블 하나만 만들어 "버전 1은 적용됨"으로 기록한다. 테이블과 데이터는 바꾸지 않는다.
4. **새 앱 배포**: 시작할 때 V2부터 자동 적용된다. `setup_key`가 이미 있는 DB(이 기능을 `update`로 먼저 받은 경우)에서도 V2는 `IF NOT EXISTS`와 존재 검사로 오류·중복 없이 지나간다.
5. **확인**: `select version, description, success from flyway_schema_history;` 가 1, 2 모두 `t`이고 `GET /api/health`가 `ok`인지 본다.

`baseline-on-migrate`는 켜지 않는다. 켜면 스키마가 다른 DB도 검사 없이 기준선이 잡혀 버린다.

## 7. 백업과 복구

- 백업: `sh scripts/backup-db.sh [폴더]` (`pg_dump`, 압축). 마이그레이션 전에 반드시 실행하고, 실행 시각과 파일 위치를 기록한다.
- 복구: `docker compose stop api` → `sh scripts/restore-db.sh <백업파일>` → `docker compose start api`. 덤프에 `flyway_schema_history`도 들어 있어 복원하면 이력도 그 시점으로 돌아간다.
- 기존 앱 버전으로 되돌리려면 DB를 마이그레이션 **이전 백업**으로 복원한 뒤 이전 이미지를 배포한다. (V2처럼 컬럼을 추가하는 변경은 이전 앱과도 호환되지만, 이력 테이블이 남아 있으므로 복원 없이 이전 앱을 띄우는 것은 권장하지 않는다.)
- 정기 백업과 외부 보관은 운영 담당이 설정한다(`공유-데이터-운영.md`).

## 8. 마이그레이션이 실패했을 때

| 증상 | 원인 | 대응 |
|---|---|---|
| `Found non-empty schema(s) … without schema history table` | 이력 없는 기존 DB | 6절 절차(비교 → baseline). 앱이나 데이터는 바뀌지 않았다 |
| `Validate failed: Migration checksum mismatch` | 적용된 V 파일을 수정함 | 파일을 원래대로 되돌리고 변경은 새 V 파일로 한다. 어쩔 수 없이 공백/주석만 바꿨다면 확인 후 `flyway repair`로 체크섬만 갱신 |
| SQL 오류로 시작 실패 | 새 마이그레이션이 데이터와 충돌(중복·NOT NULL 위반 등) | 그 파일은 트랜잭션이라 DB에 반영되지 않았다. 충돌 데이터를 확인(백업 후)하고 SQL을 고쳐 **다시 배포**. 이력에 `success=f` 행이 남았다면 `flyway repair` 후 재시도 |
| `Schema-validation: missing column/wrong column type` | Entity와 DB 불일치 | 마이그레이션이 빠졌거나 DB가 다르다. `db-schema-check.sh`로 차이를 보고 새 V 파일로 맞춘다 |
| `Detected resolved migration not applied` / 순서 오류 | 이미 적용된 번호보다 작은 번호의 새 파일 | 번호를 가장 큰 번호 + 1로 바꾼다 |

기존 데이터를 지우거나 DB를 초기화해서 해결하지 않는다. 필요하면 백업으로 복원한다.

## 9. 적용 전 충돌 가능성(식별한 항목)

- 운영 DB가 V1과 다른 경우: 과거 `update`로 생긴 잔재(더 이상 쓰지 않는 컬럼/인덱스), 다른 길이/타입, 다른 이름의 제약. → `db-schema-check.sh`가 잡는다. 현재 Entity 기준의 Hibernate 생성 스키마와 V1+V2는 컬럼·제약·인덱스 이름까지 일치함을 테스트로 확인했다(`FlywayMigrationTest`).
- 운영 DB에 이미 `setup_key`가 있는 경우: V2가 방어적으로 작성되어 문제없음(테스트로 확인).
- 기존 행의 제약 위반: V1은 새로 제약을 추가하지 않으므로 기존 행과 충돌하지 않는다.
- 운영 DB 계정 권한: Flyway는 `flyway_schema_history` 생성과 이후 DDL 권한이 필요하다(현재 compose는 `seonbi` 소유자 계정이라 충족).
- 여러 인스턴스가 동시에 시작해도 Flyway가 DB 잠금으로 한 번만 적용한다.
