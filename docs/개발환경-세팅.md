# 개발 환경 세팅

GitHub에서 저장소를 받은 뒤 누구나 같은 환경에서 실행하기 위한 방법이다. 근거는 개발기획서 11.2(Docker Compose 팀 공통 환경), 11.3(환경변수), 13.1(저장소 구조), 17.7(Spring Boot 전환)이다.

> **현재 상태 (2026-10-24)**: 백엔드를 Spring Boot 3(Java 21, Gradle)로 바꾸는 중이다. 지금 저장소에는 `docs/`와 파이썬 참조 코드(`backend/`, A가 `engine-reference/`로 이동 예정)만 있다. Spring 파일(`build.gradle.kts`, `gradlew`, `docker-compose.yml`, `Dockerfile`, `.env.example`, `.gitignore`)은 백엔드 B가 골격을 만들 때 추가한다(15.1). 그 전까지는 [임시 방법](#5-임시-방법-spring-골격이-dev에-들어오기-전)을 쓴다.

## 0. 브랜치 (최소 규칙)

- `main`은 완성본, 다 같이 쓰는 최신본은 `dev`다.
- 각자 자기 브랜치(이름은 자유)에서 작업하고, 끝나면 `dev`에 합친다.
- 남이 기다리는 것(DB 모델, `core/`, 스텁 라우터)은 먼저 작게 합친다.

```bash
git switch dev && git pull origin dev     # 최신 dev 받기
git switch -c 내-작업-이름                 # 내 브랜치 만들기
# ...작업, 커밋...
git push -u origin 내-작업-이름            # 올린 뒤 dev에 합치기
```

`dev`가 아직 원격에 없으면 처음 한 사람만 `git switch main && git switch -c dev && git push -u origin dev`로 만든다.

### `dev`는 이렇게 쓴다

`dev`는 **모두의 작업이 모이는 공용 브랜치**다. 언제 받아도 실행되는 상태를 목표로 한다.

```
내 브랜치  ── 작업 ── 작업 ──┐
내 브랜치  ── 작업 ──────────┼──▶  dev  ───(발표·제출 직전에만)───▶  main
내 브랜치  ── 작업 ── 작업 ──┘      ▲
                                   └ 합치기 전에 dev를 받아와서 충돌을 먼저 해결
```

| 상황 | 하는 일 |
|---|---|
| 새 작업을 시작할 때 | `dev`를 최신으로 받고(`git pull origin dev`) 거기서 내 브랜치를 만든다 |
| 작업이 끝났을 때 | 내 브랜치를 `dev`에 합친다. 합치기 전에 `dev`를 한 번 받아와서 충돌을 내 브랜치에서 먼저 해결한다 |
| 다른 사람의 작업이 필요할 때 | `dev`에 이미 합쳐진 것이면 `git pull origin dev`로 받는다. 아직 안 합쳐졌으면 그 사람에게 먼저 작게 합쳐 달라고 요청한다 |
| 합친 뒤 | 내 브랜치는 지운다. 다음 작업은 다시 `dev`에서 새로 시작한다 |
| `dev`가 깨졌을 때 (서버가 안 뜸, 테스트 실패) | 깨뜨린 사람이 가장 먼저 고친다. 급하면 그 합치기를 되돌린다(`git revert`). 그동안 다른 사람은 깨지기 전 커밋에서 작업한다 |
| 발표·제출 직전 | `dev`에서 서버가 뜨고 P0 흐름(결정 구성 → 질문 → 결과 → 확정)이 도는지 확인한 뒤 `main`에 합친다 |

- **`main`에는 평소에 합치지 않는다.** 발표·제출용으로 "돌아가는 시점"을 남겨 두는 용도다.
- **`dev`에서 직접 작업하지 않는다.** 작은 문서 수정 정도는 괜찮지만, 코드는 내 브랜치에서 하고 합친다. 여러 명이 같은 브랜치에서 동시에 고치면 서로 덮어쓰기 쉽다.
- **합치기 전 최소 확인**: 내가 고친 부분이 돌아가는지(엔진이면 `./gradlew test`, API면 서버를 띄워 `/swagger-ui`에서 호출) 한 번 확인한다.
- **DB 모델을 바꾼 작업을 `dev`에 합칠 때**는 팀 채팅에 "DB 초기화 필요(`docker compose down -v`)"라고 알린다(11.2).

## 1. 미리 설치할 것

| 도구 | 용도 | 확인 명령 |
|---|---|---|
| Git | 저장소 받기 | `git --version` |
| Docker Desktop | DB·API를 같은 환경으로 실행, 테스트의 Testcontainers (11.2) | `docker compose version` |
| JDK 21 | 백엔드 빌드·실행. 직접 설치하지 않아도 Gradle toolchain이 받아 준다 | `java -version` |
| Node.js 20 이상 | 프론트 담당만 | `node --version` |
| uv | 파이썬 참조 구현(`engine-reference/`)을 돌릴 때만 | `uv --version` |

- Gradle은 따로 설치하지 않는다. 저장소의 `./gradlew`(Gradle Wrapper)를 쓴다.
- IDE는 IntelliJ IDEA를 권장한다. `backend/` 폴더를 Gradle 프로젝트로 연다.
- uv 설치(참조 구현을 돌릴 사람만):

```bash
# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# Windows (PowerShell)
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

## 3. 방법 A — Docker Compose로 전체 실행 (권장)

DB와 API를 같은 버전·설정으로 띄운다. 프론트 담당이나 백엔드 전체 흐름을 확인할 때 쓴다.

```bash
cp backend/.env.example backend/.env     # Windows: copy backend\.env.example backend\.env
docker compose up --build                # 처음, 또는 의존성이 바뀐 뒤
```

- API: http://localhost:8000 (OpenAPI 문서는 springdoc이 제공하는 Swagger UI)
- DB: `localhost:5432` (DB 도구로 직접 볼 때만)
- `db`는 `postgres:16.4`, `api`는 `backend/Dockerfile`(JDK 21 멀티 스테이지)로 만든다.

자주 쓰는 명령:

| 상황 | 명령 |
|---|---|
| 평소 실행 | `docker compose up` |
| 끄기 | `docker compose down` |
| **엔티티가 바뀐 커밋을 받았는데 DB 오류가 날 때** | `docker compose down -v` 후 `docker compose up` (DB 초기화) |
| 소스를 고친 뒤 API 이미지 다시 만들기 | `docker compose up --build` |

프론트는 Compose에 없다. `frontend/`에서 Vite 개발 서버를 띄우면 `/api`가 `localhost:8000`으로 프록시된다.

## 4. 방법 B — 로컬 Gradle로 실행 (백엔드 개발용)

코드를 자주 고치고 바로 확인할 때 쓴다. DB만 Docker로 띄운다.

```bash
docker compose up db                    # DB만 실행
cd backend
./gradlew bootRun                       # API 실행 (포트 8000)
./gradlew test                          # 테스트 (Testcontainers가 DB를 띄우므로 Docker 필요)
./gradlew spotlessApply                 # 코드 포맷 자동 정리 (커밋 전에)
```

- Windows는 `gradlew.bat`을 쓴다.
- `bootRun`은 `backend/.env`를 자동으로 읽지 않는다. 로컬 실행에서는 DB 주소가 `jdbc:postgresql://localhost:5432/seonbi`다(Compose 안에서만 호스트가 `db`). 기본값이 이 주소로 설정되어 있으면 따로 지정하지 않아도 된다.
- 엔진(`com.seonbi.engine`)은 DB 없이 도는 순수 계산이라 `./gradlew test --tests '*engine*'`처럼 일부만 빠르게 돌릴 수 있다.
- IntelliJ: `backend/`를 열면 Gradle이 자동으로 가져온다. 프로젝트 JDK는 21로 맞춘다.

## 5. 임시 방법 (Spring 골격이 `dev`에 들어오기 전)

지금은 Java 프로젝트가 없다. 백엔드 B가 Spring 골격을 `dev`에 합치기 전까지 `backend/`에는 기존 파이썬 코드가 그대로 있다. 그래서 3·4번의 `docker compose`, `./gradlew`는 아직 쓸 수 없다.

이 기간에 할 수 있는 것은 파이썬 참조 구현을 uv로 돌려 보는 것뿐이다. 지금은 `backend/`에서, A가 `engine-reference/`로 옮긴 뒤에는 그 폴더에서 실행한다.

```bash
cd backend                # 이동 후에는: cd engine-reference
uv sync                   # .venv를 만들고 uv.lock에 고정된 버전 그대로 설치
uv run pytest             # 파이썬 테스트
```

- 파이썬 참조 구현은 요청 경로에서 쓰지 않는다. PyMC 검증 스크립트, 시뮬레이션 노트북, 골든 파일 생성에만 쓴다(13.1).
- 패키지를 추가할 때는 `pip install` 대신 `uv add <패키지>`를 쓰고, `pyproject.toml`과 `uv.lock`을 같이 커밋한다.
- Spring 골격이 합쳐지면 `dev`를 받아서 3·4번 방법으로 바꾼다.

## 6. 환경변수 (`backend/.env`)

`backend/.env.example`을 복사해서 쓴다. 기본값만으로 LLM 키 없이 전체 흐름이 돈다(Fake LLM). 변수 전체 목록은 기획서 11.3이 기준이다.

| 변수 | 기본값 | 설명 |
|---|---|---|
| `SPRING_DATASOURCE_URL` | `jdbc:postgresql://db:5432/seonbi` | Compose 안에서는 호스트가 `db`. 로컬 실행이면 `localhost` |
| `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD` | `seonbi` / `seonbi` | DB 접속 정보 |
| `LLM_MODEL_FAST`, `LLM_MODEL_QUALITY` | `fake:default` | `제공자:모델명` 형식. 실제 LLM을 쓸 때 `gemini:gemini-2.5-flash` 등 (6.4) |
| `LLM_FALLBACK_MODELS`, `LLM_ROUTES` | 비움 | 선택. 대체 모델, 호출 종류별 모델 |
| `GEMINI_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` | 비움 | 쓰는 제공자의 키만 자기 `.env`에 넣는다 |
| `AI_DAILY_QUOTA_PER_CLIENT` | `50` | 클라이언트 ID당 하루 AI 호출 수 (12.2) |
| `ENGINE_PARTICLES` | `4000` | 엔진 파티클 수 |

**API 키는 `.env`에만 넣고 절대 커밋하지 않는다.** `.env`는 `.gitignore`에 들어 있다. 키를 채팅·문서·코드에 붙여 넣었다면 재발급한다.

## 7. 올리지 않는 것

| 경로 | 이유 |
|---|---|
| `build/`, `.gradle/` | Gradle 빌드 결과·캐시 |
| `.idea/` | IntelliJ 개인 설정 |
| `backend/.env` | API 키가 들어간다 |
| `node_modules/` | 프론트 의존성. `npm install`로 만든다 |
| `.venv/` | 파이썬 참조 구현용. 운영체제마다 다르다. 각자 `uv sync`로 만든다 |
| `__pycache__/`, `.pytest_cache/` | 파이썬 실행 캐시 |

`build.gradle.kts`, `settings.gradle.kts`, `gradlew`, `gradle/wrapper/`, `.env.example`, `uv.lock`(참조 구현)은 **올린다.** 이 파일들이 "모두 같은 환경"의 기준이다.

## 8. 자주 생기는 문제

| 증상 | 원인·해결 |
|---|---|
| `Unsupported class file major version` 등 JDK 버전 오류 | JDK 21이 아닌 버전으로 실행 중 → `java -version` 확인, IntelliJ 프로젝트 JDK와 Gradle JVM을 21로 맞춘다 |
| 테이블·컬럼이 없다는 DB 오류 | 다른 사람이 엔티티를 바꿈(`ddl-auto=update`는 삭제·타입 변경을 반영하지 못함) → `docker compose down -v` 후 다시 실행 (11.2) |
| 포트 5432 / 8000이 이미 사용 중 | 로컬에 다른 PostgreSQL·서버가 켜져 있음 → 끄거나 Compose 포트를 바꾼다 |
| `./gradlew test`가 Docker 연결 오류로 실패 | Testcontainers는 Docker가 켜져 있어야 한다 → Docker Desktop 실행 후 다시 |
| `./gradlew: Permission denied` (macOS/Linux) | `chmod +x gradlew` |
| 포맷 검사(`spotlessCheck`)에서 실패 | `./gradlew spotlessApply` 후 다시 커밋 |
| 모든 요청이 `400 CLIENT_ID_REQUIRED` | 요청에 `X-Client-Id` 헤더(UUID)가 없음 (3.1, 7.1) |
