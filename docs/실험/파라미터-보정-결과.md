# 파라미터 보정 결과 — 질문 수·종료 기준 (개발기획서 5.10·5.11, 개선사항 3)

## 한 줄 결론

**실제 사용자 파일럿은 아직 하지 못했다(하려면 사람이 필요하다).** 대신 가상 사용자 1,800명(시나리오 2 × 노이즈 3 × 시드 2 × 150명)으로 종료 규칙 상수를 훑었다. 결과는 **현재 상수(최소 3문항 · 확신 0.85 · 정보 이득 0.03 · 상한 `max(6,2K)`)가 이미 "질문 수 대비 적중률" 곡선 위에 있어서 바꿀 근거가 없다**였다. 값을 바꾸지 않았다. 대신 파일럿 데이터를 받으면 바로 같은 판단을 할 수 있도록 집계 SQL(`scripts/pilot-report.sql`)과 보정 실험 도구(`./gradlew calibrate`)를 만들었다.

## 1. 방법

- 질문 선택(EIG)은 종료 규칙과 무관하다. 그래서 가상 사용자마다 질문을 **끝까지(12개)** 한 번만 묻고 시점별 값(1위일 최고 확률 · 정보 이득 · 1위 적중 · MAE)을 기록했다. 여러 종료 규칙을 **같은 기록 위에 다시 적용**하므로 규칙끼리 비교가 공정하다. 구현: `backend/src/test/java/com/seonbi/engine/sim/Calibration.java`.
- 가상 사용자는 엔진 자신의 우도 모델대로 답한다. 실제 사람은 더 흔들리므로 노이즈 ε(확률 ε로 무작위 응답) = 0, 0.1, 0.2 를 모두 돌렸다. 시나리오는 구매형(숫자형 위주)과 진로형(단계형·순위 위주) 둘.
- **튜닝 시드(42)와 검증 시드(1001)를 따로** 두어, 튜닝에서 고른 규칙이 새 사용자에도 통하는지 봤다. 아래 숫자는 6개 조건 평균이다.
- 훑은 범위: 최소 질문 수 {2,3,4} × 확신 임계값 {0.70, 0.75, 0.80, 0.85, 0.90, 0.95} × 정보 이득 임계값 {0.01, 0.03, 0.05, 0.08} × 질문 상한 {6, 8, 10}.
- 실행: `cd backend && ./gradlew calibrate -Pargs="--users 150"` (약 5분, Java 21).

## 2. 질문을 더 묻는 것의 효과 (규칙 없이 n개만 묻기, 튜닝 시드)

| 질문 수 | 1위 적중률 | MAE |
|---|---|---|
| 2 | 0.735 | 0.110 |
| 3 | 0.768 | 0.096 |
| 4 | 0.769 | 0.092 |
| 5 | 0.799 | 0.084 |
| 6 | 0.801 | 0.081 |
| 8 | 0.836 | 0.074 |
| 10 | 0.857 | 0.068 |
| 12 | 0.870 | 0.062 |

질문을 더 묻는 값어치는 줄어든다. 2→5문항에서는 적중이 +6.4%p(문항당 약 2%p), 5→12문항에서는 +7.1%p(문항당 약 1%p)다. 5→6문항은 +0.2%p로 거의 평평하다.

## 3. 현재 규칙과 후보 규칙 (6개 조건 평균)

| 규칙 (최소 · 확신 · 정보이득 · 상한) | 질문 수 (튜닝/검증) | 1위 적중 (튜닝/검증) | MAE (튜닝/검증) |
|---|---|---|---|
| **현재 (3 · 0.85 · 0.03 · 10)** | 5.01 / 5.08 | 0.839 / 0.859 | 0.086 / 0.084 |
| A (2 · 0.80 · 0.03 · 10) — 더 일찍 멈춤 | 4.13 / 4.17 | 0.836 / 0.850 | 0.093 / 0.090 |
| B (3 · 0.90 · 0.03 · 10) — 더 확신할 때까지 | 5.58 / 5.61 | 0.842 / 0.862 | 0.084 / 0.081 |
| C (2 · 0.95 · 0.03 · 10) — 아주 확신할 때까지 | 6.09 / 6.08 | 0.850 / 0.865 | 0.082 / 0.082 |

조건별(검증 시드):

| 조건 | 현재 | A | B | C |
|---|---|---|---|---|
| 구매 ε=0 | 4.46문항 · 0.893 | 3.65 · 0.893 | 4.85 · 0.887 | 4.81 · 0.880 |
| 구매 ε=0.1 | 4.71 · 0.867 | 3.55 · 0.860 | 5.09 · 0.867 | 4.96 · 0.860 |
| 구매 ε=0.2 | 4.83 · 0.840 | 3.65 · 0.833 | 5.15 · 0.847 | 4.94 · 0.847 |
| 진로 ε=0 | 5.51 · 0.873 | 4.86 · 0.847 | 6.27 · 0.880 | 7.08 · 0.880 |
| 진로 ε=0.1 | 5.43 · 0.840 | 4.65 · 0.827 | 6.12 · 0.860 | 7.23 · 0.880 |
| 진로 ε=0.2 | 5.55 · 0.840 | 4.69 · 0.840 | 6.21 · 0.833 | 7.47 · 0.840 |

읽는 법:

- **정보 이득 임계값(0.01~0.08)은 거의 결과를 바꾸지 않는다.** 확신 임계값이 먼저 걸리기 때문이다. 현재 0.03을 그대로 둬도 된다.
- **확신 임계값이 질문 수를 정한다.** 0.80으로 내리면 평균 0.9문항을 아끼는 대신 적중이 0.3~0.9%p 내려간다(표준오차 이내). 0.95로 올리면 1문항 이상 더 묻는데 적중은 0.6~1.1%p만 오른다. 진로형은 0.95에서 7문항 넘게 묻게 돼서 비용이 크다.
- 어느 후보도 현재 규칙보다 **질문 수·적중·MAE를 동시에 낫게 하지 못한다.** 가장 가까운 것은 최소 질문 수만 2로 낮추는 안(2 · 0.85 · 0.03 · 10)으로, 0.35문항을 아끼고 적중은 같지만(0.839/0.860) MAE가 0.003~0.004 나빠진다. 이 정도 차이는 이번 표본(조건당 150명)의 오차 안이라 **상수를 바꾸지 않는다.**
- 파일럿에서 "질문이 길다"는 반응이 많으면 A(최소 2 · 확신 0.80)가 안전한 후퇴안이다(약 0.9문항 절약, 적중 −0.3~0.9%p). "결과가 못 미덥다"는 반응이 많으면 B가 후보다. 바꿀 상수는 `Stopping.java` 맨 위의 `MIN_QUESTIONS`·`CONFIDENT_P_BEST`다(5.11).

## 4. 확신도 표시가 맞는가 — 종료 시점 "1위일 확률"과 실제 적중

현재 규칙으로 멈춘 1,800명이 종료 시점에 화면에 띄울 확률(구간 평균)과 실제 정답 1위 적중률.

| 종료 시점 확률 구간 | 사용자 수 | 평균 표시 확률 | 실제 적중률 |
|---|---|---|---|
| 0.00–0.55 | 82 | 0.494 | 0.415 |
| 0.55–0.70 | 105 | 0.621 | 0.600 |
| 0.70–0.85 | 79 | 0.763 | 0.709 |
| 0.85–0.95 | 907 | 0.899 | 0.874 |
| 0.95–1.00 | 627 | 0.984 | 0.928 |

- 전체적으로 **표시 확률이 실제보다 높다(과신).** 구간마다 2~8%p 높다(0.95 이상 구간은 5.6%p). 사용자가 실제로 흔들리는 ε가 섞여 있어서 생기는 차이다.
- 낮은 확신 배너 기준(`LOW_CONFIDENCE_P_BEST` = 0.55)은 **적절하다.** 0.55 미만 구간의 실제 적중률은 41.5%라 "추천이 불안정하다"는 안내가 맞다.
- 개선 후보(바꾸지 않음): 화면의 최대 표시 확률 상한(`MAX_SHOWN_PROBABILITY` = 0.99)을 0.95 정도로 낮추거나 "약 90% 이상"처럼 구간으로 보여 주는 방식. 실제 사용자 데이터로 같은 표를 만들어 본 뒤 정한다.

## 5. 파일럿을 하면 무엇을 보나 (이번에 만든 도구)

`scripts/pilot-report.sql`은 읽기 전용이고 제목·선택지 이름·자유 입력 원문은 읽지 않는다. 다음을 한 번에 낸다.

1. 질문 수 분포 · 평균 · 중앙값 · "잘 모르겠어요" 비율 (`answers`)
2. 답변 수정(38번) 사용량
3. 마지막 추정의 확신도 분포 (`estimate_snapshots`)
4. 확정한 선택이 추천과 같았나 (`final_choices.matched_recommendation`)
5. 확신도 구간별 추천 일치율 — 확신이 높을수록 사용자가 추천을 따르는지

판단 기준 제안(파일럿 10~20명, 사람이 직접 풀어 본 결정):

| 관찰 | 조정 |
|---|---|
| 평균 질문 수가 6을 넘고 중간에 그만둔 사람이 많다 | 후보 A로 내린다 |
| 확정한 선택이 추천과 다른 비율이 높고, 확신도가 높은 구간에서도 그렇다 | 후보 B로 올리고 확률 표시 상한을 낮춘다 |
| "잘 모르겠어요" 비율이 30%를 넘는 질문 유형이 있다 | 그 유형의 문장·선택지를 고친다(종료 상수가 아니라 질문 쪽 문제) |
| 낮은 확신 배너가 자주 뜬다 | 추가 질문 라운드(4.2)를 더 눈에 띄게 한다 |

사용법: `docker compose exec -T db psql -U seonbi -d seonbi -f - < scripts/pilot-report.sql` (파일 위쪽 `since`를 파일럿 시작 시각으로 바꿔서 점검용 결정을 제외한다).

## 6. 한계 (솔직하게)

- **가상 사용자는 엔진 자신의 모델대로 답한다.** 실제 사람은 이 모델과 다르게 답할 수 있어서 위 적중률은 실제 값이 아니라 **같은 조건에서 규칙끼리 비교하기 위한 값**이다. 절대 수치를 발표에 쓰지 않는다.
- 사용자 수(조건당 150명)가 작아 후보 사이의 0.5%p 안쪽 차이는 우연일 수 있다.
- 노이즈 ε는 "확률 ε로 무작위 응답"이라는 단순한 모양이다. 실제 사용자의 비일관성(시간이 지나면서 바뀌는 기준 등)은 담지 못한다.
- 선택지 4개·기준 5개 두 가지 문제만 돌렸다. 기준이 2~3개거나 8개 이상인 결정에서는 따로 봐야 한다.
