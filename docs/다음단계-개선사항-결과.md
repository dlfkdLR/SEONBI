## 3. 항목별 내용

### 3.1 가중치 시뮬레이션 (API 46)

- 추정 가중치를 그대로 넣으면 순위가 바뀌지 않는다.
- 한 기준에 몰아주면 그 기준의 1등이 1위가 된다. 합이 1이 아니어도 비율로 정규화한다.
- 계산만 하고 저장하지 않는다(분석 `computedAt`과 가중치가 그대로).
- 테스트: `SimulationAndEditTest`

### 3.2 답변 수정 (API 38)

- 답변을 고치면 추정이 바뀌고, 원래 답으로 되돌리면 처음 값과 **정확히 같아진다**(모든 유효 답변으로 처음부터 재추정).
- 수정해도 상태는 유지되고, 확정 뒤에는 `409 DECISION_FINALIZED`.
- 화면에서는 질문 중 "이전 답변 보기 → 수정"으로 쓴다. 결과 화면의 "조금 더 답해볼게요"로 추가 라운드에 들어가면 이어서 수정할 수 있다.

### 3.3 파라미터 보정

**실제 사용자 파일럿은 하지 못했다.** 대신 가상 사용자 1,800명(시나리오 2 × 노이즈 3 × 시드 2 × 150명)으로 종료 규칙 216가지를 같은 질문 기록 위에서 비교했다.

| 규칙 (최소 · 확신 · 정보이득 · 상한) | 평균 질문 수 | 1위 적중 | MAE |
|---|---|---|---|
| **현재 (3 · 0.85 · 0.03 · 10)** | 5.0 | 0.84~0.86 | 0.085 |
| 더 일찍 멈춤 (2 · 0.80) | 4.1 | 0.84~0.85 | 0.09 |
| 더 확신할 때까지 (3 · 0.90) | 5.6 | 0.84~0.86 | 0.083 |
| 아주 확신할 때까지 (2 · 0.95) | 6.1 | 0.85~0.87 | 0.082 |

- 질문 수·적중·MAE를 동시에 낫게 하는 후보가 없어 **상수를 바꾸지 않았다.**
- 정보 이득 임계값(0.01~0.08)은 결과에 거의 영향이 없다. 확신 임계값이 질문 수를 정한다.
- 화면에 띄우는 확률은 실제 적중률보다 구간마다 2~8%p 높다(과신). 낮은 확신 배너 기준 0.55는 적절했다.
- 한계: 가상 사용자는 엔진 모델대로 답하므로 **절대 수치를 발표에 쓰면 안 된다.** 규칙끼리 비교용이다.

**파일럿 방법**
1. 10~20명이 실제 결정을 풀어 보게 한다.
2. `docker compose exec -T db psql -U seonbi -d seonbi -f - < scripts/pilot-report.sql` 실행(파일 위쪽 `since`를 파일럿 시작 시각으로). 질문 수 분포, 건너뛰기 비율, 답변 수정 사용량, 확신도 분포, 추천 일치율을 낸다. 제목·선택지·자유 입력은 읽지 않는다.
3. 조정 기준은 `docs/실험/파라미터-보정-결과.md` 5절의 표를 따른다.
4. 바꿀 상수는 `Stopping.java` 맨 위의 `MIN_QUESTIONS`, `CONFIDENT_P_BEST`.

### 3.4 범용 AI 비교

Claude(claude-sonnet-5-5)와 GPT(gpt-5.6-sol)를 도구·코드 실행 없이 새 대화로 반복 호출했다(64회, 합성 데이터만).

| 항목 | 결과 |
|---|---|
| 전환점 정확도("몇 %에서 1위가 바뀌나") | **Claude·GPT 모두 12/12 정확**(오차 0.00%p), 3회 반복도 같은 값 |
| 가중치 추정 일관성 | 대체로 같은 값. 다만 GPT 1회, Claude 1회는 다른 값을 냄. 선비는 시드만 바꿔도 표준편차 0.6%p 안쪽 |
| 가중치 정확도(MAE) | 선비 6.1%p, Claude 7.3%p, GPT 7.7%p (사용자 4명이라 우연일 수 있음) |

- **"범용 AI는 계산이 틀린다"는 주장은 이 실험으로 뒷받침되지 않는다.** 기획서 1.5가 "결과 전에는 단정하지 않는다"고 한 그대로 실측값을 적었다.
- 이번 실험은 범용 AI에 유리하다. 슬라이더 의미, 점수표, 계산 규칙을 프롬프트에 전부 줬다.
- 재지 않은 곳에 선비의 강점이 있을 가능성이 크다: 다음 질문 선택(랜덤 대비 진로형 7.2 → 5.3문항), 불확실성(구간·1위 확률·안정성), 결정 기록.
- **발표 권장 문구:** "계산은 비슷하게 하지만, 질문을 설계하고 불확실성을 숫자로 약속하는 일은 선비의 엔진이 맡는다."
- 안 한 것: 질문 효율 실험(챗봇 인터뷰), 수치 없는 자연어 입력, 작은 모델, 대규모 표본.
- 재현: `cd backend && ./gradlew aiCompareFixture -q > fixture.json` 후 `python3 scripts/ai_compare.py run|report --fixture fixture.json --out docs/실험/범용AI-비교-원본`

### 3.5 기록 이동 (신규 API)

운영은 현재 "모든 방문자가 모든 결정을 보는" 공유 모드라 "기기를 바꾸면 기록이 사라진다"는 한계는 이미 약해졌다. 그래도 `X-Client-Id`는 작성자와 AI 호출 상한 집계 단위로 남아 있어, 기기를 바꿔도 같은 "나"로 이어가도록 만들었다.

| 번호 | API | 설명 |
|---|---|---|
| 49-1 | `POST /api/v1/transfers` | 옛 기기에서 10분짜리 일회용 코드 발급(예: `K7M2Q-9XA4B`). 새로 받으면 이전 코드 무효 |
| 49-2 | `POST /api/v1/transfers/claim` | 새 기기에서 코드 제출 → 옛 기기의 `clientId` 반환. 새 기기에 있던 결정·AI 호출 기록은 옛 ID로 **합쳐진다**(잃는 기록 없음) |

- 코드는 31글자 10자리, 서버에는 SHA-256 해시만 저장한다.
- 틀린 코드·만료·이미 사용은 모두 `404 TRANSFER_CODE_INVALID`(구분해서 알려 주지 않음). 같은 기기 5번·서버 전체 60번 틀리면 `429 TRANSFER_RATE_LIMITED`(10분 창).
- 접근 권한은 늘거나 줄지 않는다. 공유 모드에서도 호출은 된다.
- DB: `V4__transfer_codes.sql`(`transfer_codes` 테이블, `IF NOT EXISTS`). 순수 추가라 기존 데이터에 영향 없음.
- 프론트: 결정 목록의 "다른 기기로 기록 옮기기" 창(코드 받기 / 코드로 받기). 받으면 `localStorage`의 `seonbi.clientId`를 바꾸고 작성 중 임시 저장도 새 ID로 옮긴다.
- 기획서 7.2·7.3·8장·17.12, `docs/공유-데이터-운영.md`, `docs/데이터베이스-마이그레이션.md` 반영.

## 4. 팀원이 알아야 할 것

- **마이그레이션:** 배포하면 V4가 자동 적용된다. 운영 DB는 이미 Flyway로 이관됐으므로 별도 작업은 없다.
- **테스트 기대값 변경:** 테이블 수가 13 → 14개(`transfer_codes`), Flyway 적용 개수가 4개로 바뀌었다(`FoundationTest`, `FlywayMigrationTest`).
- **프론트 계약:** `frontend/tests/contracts/api-spec.json`에 49-1·49-2를 추가했다. `frontend/src/api/schema.d.ts`(생성 파일)는 아직 다시 만들지 않았다. 담당자가 필요하면 `backend/openapi.json` 기준으로 재생성한다.
- **AI 호출 상한:** 상한은 `X-Client-Id` 단위라, 기록을 이어받으면 두 기기의 사용량이 합쳐진다.
- **브랜치:** 현재 `fix/setup-double-submit`의 미병합 커밋 위에 쌓여 있다. 그 PR이 먼저 main에 들어가야 이 변경만 깔끔한 PR이 된다.
