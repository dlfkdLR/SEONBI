# 공유 데이터와 배포 구성

2026-10-25 기준 구현 및 배포 확인 기록. `docs/개발기획서.md`의 브라우저별 격리 설명은 초기 설계 기록이다.

## 요청과 데이터 흐름

- 브라우저의 React 앱은 `/api/v1/...`을 호출한다. Compose의 Nginx가 API 컨테이너로 전달한다.
- Spring Boot API는 같은 Compose 네트워크의 `db:5432`에 접속한다. PostgreSQL 데이터베이스 이름과 사용자는 `seonbi`이며, 비밀번호는 Dokploy 환경 변수 `POSTGRES_PASSWORD`에서 주입된다.
- **운영 데이터의 원본은 Dokploy 웹 패널에서 실행하는 Compose `db` 컨테이너 하나다.** PostgreSQL 데이터는 그 배포 환경의 이름 붙은 볼륨 `seonbi-pgdata`에 저장된다. DB 포트는 외부에 열지 않는다.
- 각 컴퓨터에서 별도로 `docker compose up`을 실행하면 별개의 로컬 DB 볼륨이 생기므로, 운영 데이터를 공유하려면 모두 같은 배포 주소에 접속한다. 로컬 개발 DB와 Dokploy DB는 자동 동기화되지 않는다. 로컬 Docker는 통합 테스트에만 사용했으며 운영 DB로 사용하지 않는다.
- `/api/health`의 `db: ok`는 API가 DB 연결을 만들 수 있음을 확인한다. 이 확인만으로 백업·복원 가능성이나 모든 쓰기 경로를 보증하지는 않는다.

## 공유 범위

- 모든 방문자의 비삭제 결정이 하나의 목록에 나타난다. 이전에 각 브라우저 ID로 만든 결정도 DB 행을 옮기거나 복제하지 않고 그대로 포함한다.
- 열린 목록 화면은 30초마다 다시 조회하고, 창에 돌아왔을 때 오래된 조회 결과를 새로 받는다. 편집 중인 상세 화면의 동시 수정 충돌은 별도로 해결되지 않는다.
- 누구나 결정 ID로 상세 조회, 수정, 삭제를 할 수 있다. 삭제는 `deleted_at`을 기록하는 소프트 삭제이며 목록과 상세에서 제외된다. 로그인·권한 제한은 없다.
- `X-Client-Id` UUID는 기존 API 형식 때문에 계속 보낸다. 새 결정의 `client_id`와 AI 사용량 기록에 남지만 결정 접근 권한을 제한하지 않는다. 브라우저마다 다른 ID를 써도 같은 결정 목록을 본다.
- 여러 사람이 동시에 같은 결정을 편집하면 나중에 저장된 변경이 앞선 변경을 덮거나 단계별 저장 중 충돌할 수 있다. 협업 잠금·버전 충돌 UI는 아직 없다.

## 운영에서 확인할 사항

- Dokploy Compose가 Git `main`과 `./docker-compose.yml`을 사용한다. 새 커밋이 실제 배포되었는지 배포 커밋과 서비스 상태를 비교해야 한다.
- 배포 전 PostgreSQL 볼륨의 외부 백업과 복원 절차를 마련한다. 2026-10-25 확인 당시 Dokploy Backups와 Volume Backups에 항목이 없었다.
- `spring.jpa.hibernate.ddl-auto=update`가 현재 기본값이다. 운영 스키마 변경을 자동 적용하므로 별도 마이그레이션 체계와 백업을 마련한 뒤 `validate`로 전환하는 것이 안전하다.
