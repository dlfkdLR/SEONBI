## 최신 백엔드에서 확인한 차이와 미완성 부분

1. **B의 415 오류 수정은 이미 최신 브랜치에 들어 있습니다.** 288d5e3에서 미디어 오류 406/415 보존, JSON 오류, 상태/검증, 목록 조회를 수정했습니다. 프론트도 PUT/POST/PATCH 본문이 있을 때 JSON Content-Type을 붙입니다. 실제 Spring Boot+DB 요청 검증은 별도로 필요합니다.
2. **C의 가짜 성공 문제는 0de1106에서 수정됐고 최신 d2c8504에서도 유지됩니다.** InputController의 28~30, ResultController의 47~48은 `501 NOT_IMPLEMENTED`, `details.stub=true`로 실패합니다. 서비스 구현이 끝난 것은 아닙니다. 프론트는 이를 모달 오류로 표시하고 확정/파일 저장 성공으로 처리하지 않습니다.
3. **A에는 엔진·DTO가 있지만 현재 브랜치에 질문·분석 HTTP 컨트롤러가 없습니다.** 프론트의 경로/DTO 연결과 실제 서버 엔드투엔드 동작을 구분해야 합니다. A의 HTTP·상태 전이 서비스 연결 후 31~46을 실제 요청으로 검사해야 합니다.
4. B의 OpenAPI는 구성 API만 기술합니다. A/C까지 통합해 재생성하기 전에는 생성 타입만으로 모든 질문/분석 응답을 보장할 수 없습니다. `numeric`/`free_text`의 payload·직접 답변 형식도 A와 합의해야 합니다. 현재 A는 자유 객체 payload를 허용하면서 AnswerValue에는 text 필드가 없습니다.
5. B·C·A 브랜치 간 기반 파일 충돌과 서비스 연결은 이 프론트 수정에서 합치지 않았습니다. 팀의 dev 통합에서 B 최신을 먼저 반영하고 C가 그 수정 기반을 가져온 후 A와의 충돌을 해결해야 합니다. main은 수정하지 않습니다.

## 검증과 한계

- 프로덕션 빌드 및 TypeScript 검사.
- 42개 메서드/경로와 B OpenAPI의 실제 경로가 일치하는지 검사.
- 요청/오류/파일·ID 이전·값/순위·발급 ID 치환·부분 저장 재시도 단위 검사.
- 테스트 HTTP 응답을 사용하는 Chrome 검사: 생성→구성→값/조건 PUT→서버 질문→서버 분석→서버 시뮬레이션→확정→Markdown→복제. 예시 숨김/복원, 네트워크 실패, 501 실패, 한글 IME 포함.
- 실제 백엔드 통합 검사는 **미실행**. 검사 시 이 컴퓨터의 Docker daemon이 꺼져 있었고, A/C의 서비스 연결도 미완성이었습니다. 따라서 실제 서버 분석 수치, DB 소유권/트랜잭션, 서버의 중복 질문 방지까지 검증했다고 주장하지 않습니다.

## 백엔드 통합 뒤 필요한 실제 검사

- `/api/health`의 DB ok, 프록시 경유 목록/상세와 동일 X-Client-Id 유지.
- B의 415/406 및 필드별 검증 응답을 실제 요청으로 확인.
- 값/동순위/조건 저장 → 상세 재조회 → 질문 시작의 readiness.
- 답변 제출·수정·건너뛰기·종료 → A의 분석 결과와 화면 수치 일치.
- C의 추출/확인/거절·확정·내보내기가 501에서 실제 서비스 응답으로 바뀌는지 확인.
- 확정 잠금, 복제 ID 분리, 삭제, 클라이언트 ID가 다른 요청의 404.

## 최신 C API 훅과의 추가 비교

C의 d2c8504가 추가한 질문 타입은 spec/display를 쓰지만, 기획서 7.3과 A의 QuestionDtos는 title/payload를 씁니다. 화면은 후자를 기준으로 연결했습니다. C의 훅 파일을 무조건 복사해 중복 Query 캐시를 만들지 않고, 화면이 사용하는 훅과 전송을 한 벌로 유지합니다. C의 inputs/results 헬퍼, ID fallback, inputText 검증을 합쳤으며 C가 관리하는 schema.d.ts는 그대로 둡니다. 다음 C 동기화 때 기존 http.ts를 덮어쓰지 말고 이 통합본을 기준으로 반영해야 합니다.
